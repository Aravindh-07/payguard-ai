# PayGuard AI

**Intelligent Payment Fraud Detection & Risk Scoring System**

> Built for the Razorpay AI Builder Internship 2026 submission.
> This is an educational/prototype fraud detection system and is **not connected to or endorsed by Razorpay**.

---

## Overview

PayGuard AI is an end-to-end, runnable prototype that analyzes payment transaction
data, predicts the likelihood of fraud, converts that likelihood into a 0–100 risk
score, classifies transactions as **LOW / MEDIUM / HIGH** risk, and explains *why*
a transaction was flagged — all through a fintech-style Streamlit dashboard and a
FastAPI backend.

## Problem Statement

Payment platforms process a huge volume of transactions, and only a small fraction
are fraudulent — but the cost of missing fraud (chargebacks, lost trust, regulatory
exposure) is far higher than the cost of double-checking a legitimate transaction.
This makes fraud detection a classic **imbalanced classification** problem: naive
accuracy-driven models look great on paper while missing almost all real fraud.
Reviewers and analysts also need to *understand* why a transaction was flagged,
not just get a black-box label.

## Solution

PayGuard AI addresses this with:
1. A machine learning model trained specifically to prioritize catching fraud
   (recall) while keeping false positives manageable.
2. A transparent 0–100 risk score derived directly from the model's fraud
   probability (never randomly generated).
3. A rule-based explainability layer that surfaces the specific behavioral
   signals driving each score.
4. Two access points — a dashboard for human analysts and a REST API for
   integration into other systems.

## Key Features

- Synthetic, realistic, non-perfectly-separable transaction dataset (50,000 rows)
- Trains and compares Logistic Regression, Random Forest, and XGBoost
- Model selection based on **F2-score** (recall-weighted), not accuracy
- Fraud probability → 0–100 risk score → LOW / MEDIUM / HIGH classification
- Rule-based "Why?" explanation for every prediction
- Streamlit dashboard: analytics overview, manual transaction analyzer, filterable transaction table
- FastAPI backend with `/predict` and `/health`, full Pydantic validation, auto-generated docs
- SQLite logging of every analyzed transaction
- Automated pytest test suite (model + API)
- Clean, documented, modular codebase

## Architecture

```
User
  |
  v

  |
  v
Input Validation (Pydantic)
  |
  v

  |

  |

  |

  |

  |

```

The dashboard and the API both call the **same** `predict_transaction()` function
in `app/predictor.py`, so scoring logic is defined exactly once.

## Machine Learning Approach

**Models trained and compared:** Logistic Regression, Random Forest, XGBoost.

**Why not accuracy?** The dataset is ~97% legitimate transactions. A model that
predicts "not fraud" for everything would score >97% accuracy while catching zero
fraud — accuracy alone is not an acceptable metric here.

**Selection criterion:** the model with the highest **F2-score** (F-beta, β=2) on
a held-out, stratified test set is selected automatically. F2 weights recall about
4x more heavily than precision, reflecting the business reality that missing real
fraud is costlier than flagging a legitimate transaction for review — while still
penalizing a model that has *no* precision at all (i.e. it won't select a model
that just flags everything). Precision, recall, F1, ROC-AUC, PR-AUC, and the
confusion matrix are all computed and stored for every candidate model, not just
the winner, so the trade-offs are fully visible in `models/model_metadata.json`.

Class imbalance is handled via `class_weight="balanced"` (Logistic Regression,
Random Forest) and `scale_pos_weight` (XGBoost), rather than naive oversampling,
to keep the pipeline simple and reproducible.

## Dataset

**The dataset is entirely synthetic**, generated by `src/data_generator.py` with a
fixed random seed (42) for reproducibility. It is **not** real banking or Razorpay
data. It is constructed so that:
- Fraud is rare (~2.8% of transactions), matching real-world class imbalance.
- Fraud risk is driven by a weighted combination of behavioral signals (device
  novelty, IP risk, velocity, distance from usual location, prior fraud history,
  odd hours, etc.) plus random noise, so the classes are **not perfectly
  separable** — a realistic, non-trivial ML problem.
- ~1% of values are missing, forcing a real imputation step in preprocessing.

18 features are generated per transaction (see `src/preprocessing.py` for the
canonical feature list), covering transaction details, customer history, device/
location signals, and behavioral velocity indicators.

## Model Comparison

Results from the training run bundled in this repo (`models/model_metadata.json`),
evaluated on a stratified 20% held-out test set (10,000 transactions):

| Model | Precision | Recall | F1 | F2 | ROC-AUC | PR-AUC |
|---|---|---|---|---|---|---|
| Logistic Regression | 0.102 | 0.755 | 0.179 | 0.330 | 0.865 | 0.253 |
| Random Forest | 0.257 | 0.248 | 0.253 | 0.250 | 0.855 | 0.186 |
| **XGBoost (selected)** | **0.168** | **0.468** | **0.247** | **0.345** | 0.835 | 0.205 |

XGBoost was selected for the best balance under the F2 criterion — it catches
nearly half of all fraud in the test set while keeping precision high enough
(~17%, i.e. roughly 1 in 6 flagged transactions is truly fraudulent) to be usable
by a human review team, whereas the Logistic Regression's aggressive recall came
at the cost of flooding reviewers with false positives (~90% false-positive rate
among flags).

*Exact numbers will vary slightly if you regenerate the dataset or retrain, since
model fitting has some inherent variance even with a fixed seed across library
versions — rerun `python src/evaluate.py` to see your local results.*

## Explainability

PayGuard AI includes a **rule-based, prototype explainability layer**
(`src/explain.py`) that inspects the raw transaction fields against a set of
documented, human-readable risk rules (unusual amount, new device, high IP risk,
high velocity, failed attempts, odd hours, prior fraud history, etc.) and returns
the top triggered reasons, ranked by severity.

**This is explicitly not a SHAP or LIME explanation** — it does not perform
formal feature attribution against the trained model's internals. It is a
transparent, auditable substitute that is easy to reason about and fast to run.
See "Future Improvements" below for how to add true SHAP-based explanations.

## Limitations

- **Synthetic dataset**: all transaction data is programmatically generated, not
  real banking or Razorpay data. Real-world fraud patterns are more complex and
  adversarial (fraudsters actively adapt to detection systems).
- **Prototype model**: trained on one synthetic snapshot with a straightforward
  feature set; not tuned for production-scale precision/recall requirements.
- **Not production payment infrastructure**: no PCI-DSS compliance, no real
  authentication/authorization layer, no encryption-at-rest for the SQLite log,
  no rate limiting.
- **Rule-based explanations**, not formal model attribution (see Explainability).
- Model performance depends heavily on data quality and would need re-validation
  against real transaction data before any production use.

## Security Notes

- No API keys, credentials, or secrets are hardcoded anywhere in this repository.
- `.env` is git-ignored; `.env.example` documents optional configuration only —
  nothing in this project currently requires a `.env` file to run.
- All API inputs are validated via Pydantic (types, ranges, required fields).
- This project stores no real payment credentials, card numbers, or PII —
  only synthetic behavioral/transaction fields.
